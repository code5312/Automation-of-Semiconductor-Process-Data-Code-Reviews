# 반도체 공정 데이터 정합성 검증 자동화 — 최종 프로젝트 설계서

**부제**: 공정 데이터를 다루는 분석 코드의 도메인 특화 검증 시스템
**팀명**: GOAT (Gachon Oriented AI Transformation)
**소속 프로그램**: 대학 연합 AI 직무 프로젝트 (U3 AI 직무 코어)
**팀 인원**: 6인 (백엔드/보안 전공 1인, 반도체·신소재·기계공학·산업공학 등 배경 5인)
**진행 기간**: 약 2개월 (8주, MVP) + 이후 CI/CD 단계적 적용
**문서 상태**: 최종안 v1.0 (2026-09-27)

---

## 1. 한눈에 보기

**한 줄 정의**
반도체 공정 데이터를 가공하는 파이썬 코드가 **공정 데이터의 세 가지 불변 조건 — 물리량(단위), 시간(센서·이벤트 정렬), 계보(로트·웨이퍼 입도)** — 을 깨뜨리는지 PR 단계에서 자동으로 검증하는 시스템.

**핵심 관점**
검사하는 대상은 코드지만, **지키려는 대상은 공정 데이터**다. 일반 코드 리뷰가 "코드가 문법적으로·보안상 올바른가"를 묻는다면, 이 시스템은 "이 코드가 공정 데이터를 물리적·공정적으로 올바르게 다루는가"를 묻는다.

| | 일반 코드 리뷰 도구 | 본 프로젝트 |
|---|---|---|
| 던지는 질문 | 코드가 올바른가 | 공정 데이터가 올바르게 변환되는가 |
| 필요한 지식 | 언어 문법, 보안 패턴, 코드 스멜 | 공정 파라미터 단위, 센서 샘플링 주기, 로트/웨이퍼 계보 |
| 지식의 위치 | 도구 내장 규칙 | 팀이 작성하는 **공정 데이터 계약(YAML)** |
| 탐지 결과 | 버그·취약점·스타일 | 공정 불변 조건 위반 + 공정 맥락의 수정 제안 |

**왜 필요한가**
세 가지 위반은 모두 **에러 없이 실행되고, 조용히 틀린 숫자만 만든다.** 그 숫자는 SPC 관리한계선, FDC 알람 기준, 수율 리포트로 이어지며, 결국 공정 조치 판단의 근거가 될 수 있다(가설 — 3.3절 참고).

**어떻게**
공정 데이터 계약(YAML) + 정적 규칙(확정 판정) + LLM(애매한 경우만) + 사람 승인. 자동 수정·설비 제어는 하지 않는다.

**산출물**
8주 MVP: 3개 체커, PR 코멘트/Slack 리포트, 검증 실험 결과. 이후 CI/CD 파이프라인에 단계적으로 편입(12절).

## 2. 배경 — 이 주제에 도달한 과정

팀은 초기에 취약점 도달가능성 분석 등 "독창성" 위주의 자동화 아이디어를 탐색했으나, Endor Labs, Snyk 등 상용 도구가 이미 해당 기능을 제공하고 있음을 확인하고 방향을 전환했다. 이후 전략을 **"독창성" 중심에서 "실무 자동화 + 실증" 중심**으로 재설정했다.

도메인은 반도체를 유지하되, 자동화 대상을 "공정 자체"가 아니라 **"공정 데이터가 분석 결과로 바뀌는 지점 — 즉 엔지니어가 작성하는 데이터 가공 코드"**로 좁혔다. 공정 데이터는 설비 센서, MES 이벤트, 계측 장비라는 서로 다른 출처에서 오고, 이들이 처음 만나는 곳이 엔지니어의 파이썬 스크립트다. 데이터 정합성이 깨지는 곳도 대부분 여기라는 것이 이 프로젝트의 출발점이다.

## 3. 문제 정의

| 구분 | 내용 |
|---|---|
| 사용자 | 반도체 fab의 공정 데이터 엔지니어 / FDC·SPC 담당자 / 수율 분석 엔지니어 |
| 상황 | SPC 관리도, FDC 룰, 수율/결함 분석용 파이썬 스크립트를 작성·수정할 때 |
| 작업 | 공정 데이터의 단위 일관성, 센서·이벤트 시계열 정렬, 로트/웨이퍼 조인 입도를 사람이 매번 눈으로 검토하는 작업 |
| 병목 | 일반 AI 코드리뷰 도구(Copilot, SonarQube 등)는 문법 오류·보안 취약점은 잡지만, "이 값이 반도체 공정에서 물리적으로 말이 되는 값인지"는 판단하지 못함 |
| 성과 | 공정 데이터 계약 기반 규칙(정적 규칙 + LLM 문맥 판단)으로 세 가지 공정 데이터 오류를 사전에 자동 탐지 |
| 범위 | 자동 코드 수정이나 설비 제어 개입은 제외, 탐지 + 수정 제안까지만 |

### 3.1 공정 데이터가 분석 결과가 되기까지

```
 [설비 센서]            [MES 이벤트]              [계측·검사]
 FDC trace             로트 이력, step 시작/종료    막두께, CD, 결함
 (고빈도, 장비별 주기)   (이벤트 단위)             (표본 웨이퍼·사이트만 측정)
      │                     │                        │
      └──────────┬──────────┴────────────┬───────────┘
                 ▼                       ▼
      ┌─────────────────────────────────────────────┐
      │   엔지니어의 파이썬 스크립트 (정제·병합·집계)      │  ◄── 본 프로젝트의 검사 지점
      └─────────────────────────────────────────────┘
                 │
                 ▼
     SPC 관리도 / FDC 룰 / 수율 리포트
                 │
                 ▼
     공정 조치 판단 (장비 점검, 로트 홀드, 파라미터 조정 등)
```

세 출처의 데이터는 **단위 체계, 시간 해상도, 데이터 입도(grain)가 모두 다르다.** 스크립트는 이 차이를 맞춰야 하는 유일한 지점이고, 맞추지 못해도 에러가 나지 않는다.

### 3.2 공정 데이터의 세 가지 불변 조건과 깨지는 방식

| 불변 조건 | 공정 데이터 맥락 | 깨지는 예 | 왜 에러가 안 나는가 |
|---|---|---|---|
| **물리량 정합성** | 챔버 압력(mTorr/Torr/Pa), 가스 유량(sccm/slm), 막두께(Å/nm), 온도(°C/K) | 장비 A는 mTorr, 장비 B는 Pa로 로깅된 압력을 합쳐 하나의 관리한계 계산 (1 mTorr ≈ 0.133 Pa) | 둘 다 float라 연산이 그대로 수행됨 |
| **시간 정합성** | FDC trace(장비·센서별 주기 상이), MES step 구간, 사후 계측 | 샘플링 주기가 다른 두 센서를 timestamp 정확 일치로 병합, 또는 step 구간 경계를 잘못 잡아 다른 step의 센서값이 섞임 | 매칭 안 된 행은 조용히 빠지거나 NaN이 됨 |
| **계보·입도 정합성** | Lot → Wafer → Site/Die, step·chamber 이력 | 웨이퍼 단위 두 테이블을 `lot_id`만으로 조인해 행이 곱해짐, 표본 측정된 계측 데이터와 inner join해 미측정 웨이퍼가 수율 분모에서 사라짐 | pandas `merge`는 다대다 조인을 기본 허용함 |

### 3.3 근거 수준 구분

- **구조적으로 타당한 주장**: 범용 코드리뷰 도구는 설계 목적(문법·보안 중심)상 공정 데이터의 단위·시간·입도 의미를 판단하지 못한다. 위 표의 "왜 에러가 안 나는가" 열도 언어·라이브러리 동작 자체에 근거한 사실이다.
- **가설로 다루는 주장**: 이 오류들이 실제 fab에서 원인규명 지연이나 수율 오판으로 이어졌다는 인과적 주장은 직접 사례 근거를 확보하지 못했다. 이 설계서 전체에서 "~로 이어질 수 있다" 수준으로만 표현하며, 11.1절의 실증 사례 수집으로 근거를 보강한다.
- 일반 AI 코드리뷰 도구의 탐지율 등 외부 벤치마크 수치는 근거가 없으므로 제시하지 않고, 필요한 수치는 11절에서 직접 측정한다.

### 3.4 이 문제가 반복되는 이유

- **크래시가 없는 오류다.** 일반 버그는 터져서 바로 드러나지만, 이 오류들은 리포트가 나간 뒤에야 발견되거나 발견되지 않을 수 있다. — *구조적으로 타당*
- **수정 주기가 빠르다.** SPC/FDC 룰은 공정·장비 변경 때마다 수정되는 스크립트라 매번 시니어가 단위·조인을 검토하기 어렵다. — *가설, 인터뷰로 빈도 확인 필요*
- **공정 데이터 지식이 암묵지다.** "이 센서는 몇 초 주기인가", "이 계측은 웨이퍼 몇 장을 표본으로 재는가" 같은 정보는 문서화되지 않고 선임에게만 있는 경우가 많다. — *가설, 검증 필요*

## 4. 실무에서 무엇이 바뀌는가

| 실무 지점 | 지금 | 도입 후 | 근거 수준 |
|---|---|---|---|
| PR 리뷰 | 시니어가 단위·시간·조인을 전부 눈으로 대조 | 확정 위반은 자동 판정, 시니어는 애매한 케이스만 검토 | 11.4절에서 리뷰 시간 측정 |
| 오류 발견 시점 | 이상한 관리도·수율 수치로 뒤늦게 발견될 수 있음 | PR 단계에서 발견 | 조기 발견은 구조적으로 타당, 재작업 비용 절감은 가설 |
| 공정 데이터 지식 전달 | 선임의 암묵지 | 공정 데이터 계약(YAML) + 위반 사유가 신입에게 즉시 피드백 | 정성적 효과, 측정 범위 밖 |
| 사후 추적 | "왜 이렇게 짰는지" 근거가 남지 않음 | 판정 이력·규칙 버전이 SQLite에 기록 | 기능 구현으로 확인 |

사용자별로 보면:
- **FDC·SPC 담당자**: 룰 수정 시 단위 혼용·센서 정렬 오류를 PR 단계에서 차단
- **수율 분석 엔지니어**: 조인 입도·계측 커버리지 문제로 수율 분모가 조용히 바뀌는 것을 방지
- **공정 데이터 엔지니어**: 공정 데이터 계약을 단일 기준으로 삼아 여러 스크립트의 일관성 유지

## 5. 왜 범용 코드리뷰나 "LLM에 그냥 물어보기"가 아닌가

### 5.1 범용 코드리뷰와의 차이 — 관점의 차이

범용 도구는 코드만 본다. 이 시스템은 **코드가 어떤 공정 엔티티(FDC trace, 웨이퍼 테이블, 계측 테이블)를 어떤 입도로 다루는지 추적하고**, 그 흐름을 공정 데이터 계약과 대조한다(8절, 9.2절). 같은 `merge` 한 줄이라도 범용 도구에게는 정상 코드지만, 이 시스템에게는 "웨이퍼 입도 테이블을 로트 키로만 조인한 계보 위반"이 된다.

### 5.2 LLM 단독과의 차이

1. **결정론성** — LLM 단독 판단은 같은 코드에도 결과가 달라질 수 있다. 확정 위반은 규칙 엔진이 항상 같은 결과를 낸다. 이 차이가 12절의 CI/CD 게이트 설계의 전제가 된다.
2. **비용·속도** — 확정 위반은 규칙으로 즉시 처리하고 애매한 것만 LLM을 호출한다.
3. **공정 지식의 재사용** — 프롬프트 텍스트에 파묻힌 지식 대신, 버전 관리되는 공정 데이터 계약으로 fab·장비별 규칙을 관리한다.
4. **감사 가능성** — 규칙 기반 판정은 "어떤 규칙, 어떤 계약 버전에 의해 위반인지"가 고정되어 품질 감사 근거가 된다.
5. **무인 자동화** — 사람이 복붙해서 묻는 수작업이 아니라, PR 이벤트에 자동으로 걸리는 파이프라인이다.
6. **개선 루프** — 오탐·미탐이 계약 수정 제안으로 쌓이고, 사람이 승인하면 시스템이 개선된다.

이 여섯 가지는 주장에 그치지 않고 11.3절의 **LLM-only baseline 비교 실험**으로 검증한다.

KLA Klarity, Synopsys Fab.da 등은 공정 데이터와 수율 결과 자체를 분석한다. 본 프로젝트는 그 결과를 만들어내는 **변환 로직(엔지니어의 코드)이 공정 데이터를 올바르게 다루는지**를 검사한다. 즉 경쟁 관계가 아니라, 데이터 분석 도구 앞단에서 입력의 정합성을 지키는 **보완 관계**에 가깝다.

## 7. 프로젝트 범위 (MVP)

### 7.1 검사 규칙 후보 5개 → 3개로 좁힌 과정

초기 후보: ①단위 일관성 ②시계열 정렬 ③조인 키 무결성 ④임계값 하드코딩 탐지 ⑤결측치 처리 검증(`fillna(0)`)

채택 기준: **"일반 도구나 코딩 컨벤션 문서로는 해결되지 않고, 반드시 공정 데이터 지식이 있어야 판단 가능한 것"**

- **임계값 하드코딩 탐지 → 제외**: SonarQube 등이 오래전부터 잡아온 일반 코드 스멜이며, 판단에 공정 지식이 필요 없다.
- **결측치 처리 검증 → 제외**: `fillna(0)` 패턴 하나에 국한된 좁은 규칙으로, 팀 코딩 컨벤션 문서로 충분하다.

두 항목의 제외는 기능이 부족해서가 아니라 "공정 데이터 특화"라는 차별점에 기여하지 않기 때문이다. 남은 세 규칙은 정확히 3.2절의 **세 가지 공정 데이터 불변 조건**에 대응한다.

### 7.2 채택된 3개 규칙

| 규칙 | 지키는 불변 조건 | 규칙 ID 접두어 |
|---|---|---|
| 단위 일관성 검사 (unit_checker) | 물리량 정합성 | `FAB-U` |
| 시계열 정렬 검증 (timeseries_checker) | 시간 정합성 | `FAB-T` |
| 조인 입도 무결성 검사 (join_checker) | 계보·입도 정합성 | `FAB-J` |

조인 검사는 "단순 행 수 변화 감지"가 아니라, **로트-웨이퍼처럼 정상적인 관계인지를 공정 데이터 계약으로 판단**하는 것에 한정한다.

### 7.3 확장 옵션 (5주차 이후 여유 시)

unit_checker의 변수명 매칭은 `pressure_torr`처럼 이름은 명확한데 실제 값이 다른 단위로 들어간 경우를 잡지 못한다. 여유가 있으면 `pint` 단위 라이브러리를 도입해, 함수 시그니처·docstring의 단위 명시를 기준으로 검증하는 방식을 시도한다. MVP 범위에는 포함하지 않는다.

### 7.4 명시적 비범위

- 코드 자동 수정, 설비 제어 개입
- 실제 fab 운영 데이터 직접 접근 (합성 데이터로 대체, 11.2절)
- 탐지 결과의 최종 판단 (항상 사람이 수행)

## 8. 핵심 설계 — 공정 데이터 계약 (Process Data Contract)

이 프로젝트를 범용 코드리뷰와 가르는 핵심 구성요소다. 공정 데이터에 대한 도메인 지식을 코드가 아닌 **버전 관리되는 YAML 계약**으로 분리하고, 모든 체커가 이 계약을 기준으로 판단한다.

### 8.1 계약의 구성

| 구성 | 내용 | 사용하는 체커 |
|---|---|---|
| `unit_families` | 물리량별 허용 단위 (압력, 유량, 온도, 두께 등) | unit_checker |
| `parameters` | 공정 파라미터 ↔ 물리량 매핑, 변수/컬럼명 패턴 | unit_checker |
| `entities` | 공정 엔티티별 키, 입도(grain), 샘플링 주기, 시간 윈도우, 측정 커버리지 | timeseries_checker, join_checker |
| `relationships` | 엔티티 간 기대 카디널리티 (예: lot:wafer = 1:N) | join_checker |
| `sources` | 파일/테이블 이름 패턴 → 공정 엔티티 매핑 | 데이터 흐름 추적 (9.2절) |

### 8.2 계약 예시 (구조 설명용, 실제 값은 도메인 팀원이 작성)

```yaml
contract_version: "0.1.0"

unit_families:
  pressure:    [mTorr, Torr, Pa]
  gas_flow:    [sccm, slm]
  temperature: [degC, K]
  thickness:   [angstrom, nm]

parameters:
  chamber_pressure: { family: pressure,  name_patterns: ["*pressure*", "*_pres_*"] }
  gas_flow:         { family: gas_flow,  name_patterns: ["*flow*", "*mfc*"] }
  film_thickness:   { family: thickness, name_patterns: ["*thk*", "*thickness*"] }

entities:
  lot:        { key: [lot_id], grain: lot }
  wafer:      { key: [lot_id, wafer_id], grain: wafer, parent: lot }
  step_event: { key: [lot_id, wafer_id, step_id], grain: wafer_step,
                time_window: [step_start, step_end] }
  fdc_trace:  { key: [tool_id, chamber_id, timestamp], grain: time,
                sampling_period: per_sensor }      # 센서별 주기는 별도 표로 관리
  metrology:  { key: [lot_id, wafer_id, site_id], grain: site,
                coverage: sampled }                # 표본 웨이퍼·사이트만 측정

relationships:
  - { from: lot,   to: wafer,     cardinality: "1:N" }
  - { from: wafer, to: metrology, cardinality: "1:N", coverage: sampled }

sources:
  - { pattern: "fdc_*",       entity: fdc_trace }
  - { pattern: "*metrology*", entity: metrology }
  - { pattern: "*lot_hist*",  entity: step_event }
```

### 8.3 계약으로 분리하는 이유

1. **도메인 팀원이 코드 없이 작성·검토**할 수 있다 — 반도체 배경 5인이 시스템의 핵심 로직을 직접 채운다.
2. fab·장비마다 다른 단위 체계와 샘플링 주기를 **재배포 없이 계약 변경만으로** 대응한다.
3. 계약에서 **합성 공정 데이터를 생성**해 검증·테스트에 쓴다 (11.2절, 12절 Phase 2).
4. 계약 변경 자체를 **PR로 관리**해 CI/CD에 편입할 수 있다 (12절).

## 9. 시스템 아키텍처

### 9.1 파이프라인

```
[코드 입력]  PR diff 또는 전체 스캔
      │
      ▼
[AST 파싱]  Python ast 표준 라이브러리
      │
      ▼
[공정 데이터 흐름 추적] ◄──── [공정 데이터 계약 (YAML, 버전 관리)]
  어떤 DataFrame이 어떤 공정 엔티티를              │
  어떤 입도로 담고 있는지 식별·전파                  │
      │                                       │
      ▼                                       │
[정적 규칙 엔진] ◄─────────────────────────────┘
  ├─ unit_checker        (물리량 정합성)
  ├─ timeseries_checker  (시간 정합성)
  └─ join_checker        (계보·입도 정합성)
      │
      ├── 확정 위반 ──────────────────► [error: 규칙 판정]
      ├── 애매한 후보 ──► [LLM 문맥 판단] ──► [warning: 확정 또는 기각]
      └── 판정 불가 ──────────────────► [info: 사람 확인 요청]
                          │
                          ▼
              [병합 · 신뢰도 스코어링 · SQLite 기록]
                          │
                          ▼
              [리포트 생성 (JSON + Markdown, 규칙 ID 포함)]
                          │
          ┌───────────────┼────────────────┐
          ▼               ▼                ▼
   [GitHub PR 코멘트]  [Slack 알림]   [CI 상태 체크 — 12절 Phase 2]
```

### 9.2 공정 데이터 흐름 추적

체커가 공정 관점에서 판단하려면, 먼저 **각 DataFrame이 어떤 공정 엔티티를 어떤 입도로 담고 있는지** 알아야 한다.

- **로드 지점 식별**: `read_csv`, `read_parquet`, `read_sql` 등의 인자(파일명·테이블명)를 계약의 `sources` 패턴과 대조해 엔티티를 부여한다.
- **전파**: 단순 할당, 필터링, 컬럼 선택은 입도를 유지한다. `groupby(keys).agg(...)`는 **groupby 키가 새로운 입도**가 된다 (예: metrology를 `[lot_id, wafer_id]`로 집계하면 wafer 입도로 바뀜).
- **한계와 처리**: 동적 컬럼명, 파일 간 함수 전달, 복잡한 제어 흐름은 정적으로 추적하기 어렵다. 이 경우 조용히 통과시키지 않고 **"판정 불가(info)"**로 명시해 사람에게 넘긴다. MVP는 단일 파일·단순 할당 체인을 우선 지원한다.

### 9.3 체커별 상세

#### ① unit_checker — 물리량 정합성 (`FAB-U`)

- **정적 확정**: 계약상 같은 물리량 family인데 서로 다른 단위 토큰을 가진 변수·컬럼 간 산술, 비교, concat, 또는 concat 후 단일 통계(관리한계 등) 계산
- **LLM 위임**: 이름에 단위가 없는 경우(`p1`, `val`) — 주석, 인접 변수, 함수명, 소스 파일 문맥으로 판단
- **예시**

```python
pressure_a = tool_a_df["chamber_pressure_mtorr"]
pressure_b = tool_b_df["chamber_pressure_pa"]
combined = pd.concat([pressure_a, pressure_b])
ucl = combined.mean() + 3 * combined.std()   # FAB-U001: 단위가 섞인 채 관리한계 계산
```

- **수정 제안**: 한쪽을 명시적으로 변환한 뒤 결합, 또는 (확장 옵션) `pint`로 단위를 타입에 포함

#### ② timeseries_checker — 시간 정합성 (`FAB-T`)

- **정적 확정**: 계약상 샘플링 주기가 다른 `time` 입도 엔티티끼리 timestamp 정확 일치로 병합, step 단위 집계인데 `step_event`의 시간 윈도우를 쓰지 않음
- **LLM 위임**: `merge_asof`나 `resample`이 있어도 tolerance·리샘플 주기가 계약의 샘플링 주기 대비 적절한지, 장비 간 시간대·시계 동기화 처리가 있는지
- **예시**

```python
merged = rf_power_df.merge(gas_flow_df, on=["tool_id", "timestamp"])
# FAB-T001: 샘플링 주기가 다른 두 센서를 정확 일치로 병합 → 대부분 행이 조용히 사라질 수 있음
```

- **수정 제안**

```python
merged = pd.merge_asof(
    rf_power_df.sort_values("timestamp"),
    gas_flow_df.sort_values("timestamp"),
    on="timestamp", by="tool_id",
    direction="nearest",
    tolerance=pd.Timedelta(...),   # 계약에 정의된 샘플링 주기 기준으로 설정
)
```

#### ③ join_checker — 계보·입도 정합성 (`FAB-J`)

- **정적 확정**: 두 엔티티의 입도에 필요한 키가 조인 키에서 빠짐(예: wafer 입도끼리 `lot_id`만으로 조인 → 다대다), `coverage: sampled` 엔티티와 inner join한 결과가 수율 분모 계산에 사용됨
- **LLM 위임**: 계약에 없는 테이블 조합 → 관계를 추론해 **계약 추가를 제안**. 제안은 사람이 승인해야만 계약에 반영된다(`/rules/propose` → `/rules/{id}/approve`).
- **예시**

```python
wafer_yield = yield_df.merge(metrology_df, on="lot_id")
# FAB-J001: wafer 입도 키 누락 → 로트 내 웨이퍼 수만큼 행이 곱해질 수 있음
# FAB-J002: 표본 측정 계측과 inner join → 미측정 웨이퍼가 결과에서 빠짐
```

- **수정 제안** — 입도를 먼저 맞추고, 관계를 명시적으로 검증

```python
wafer_metro = (metrology_df
               .groupby(["lot_id", "wafer_id"], as_index=False)["thickness_nm"].mean())
wafer_yield = yield_df.merge(
    wafer_metro, on=["lot_id", "wafer_id"],
    how="left", validate="1:1", indicator=True,   # 미측정 웨이퍼는 _merge 컬럼으로 식별
)
```

### 9.4 판정 등급과 신뢰도

| 등급 | 출처 | 의미 | CI/CD에서의 취급 (12절) |
|---|---|---|---|
| `error` | 정적 규칙 확정 | 계약 기준 명백한 불변 조건 위반 | Phase 2부터 머지 차단 가능 |
| `warning` | LLM 문맥 판단 | 위반 가능성 높음, 판단 근거 첨부 | 항상 advisory (차단 안 함) |
| `info` | 판정 불가 | 흐름 추적 실패 등으로 판단 보류 | 항상 advisory |

### 9.5 리포트 예시 (PR 코멘트)

```
🔴 [FAB-J001] 조인 입도 위반 — error (정적 규칙, contract v0.1.0)
yield_report.py:42

wafer 입도 테이블 `yield_df`와 site 입도 테이블 `metrology_df`를 `lot_id`만으로 병합하고 있습니다.
계약상 wafer 키는 [lot_id, wafer_id]이므로 로트 내 웨이퍼 수만큼 행이 곱해질 수 있습니다.

제안: metrology를 wafer 입도로 먼저 집계한 뒤
      on=["lot_id", "wafer_id"], validate="1:1" 로 병합
      (표본 측정 데이터이므로 how="left" + indicator 사용 권장)
```

## 11. 검증 계획

### 11.1 실무 프로세스 이해 + 실증 사례 수집 (1주차)

- 세 가지 오류가 현재 어떻게 수작업으로 검증되는지(엑셀/노트북 값 대조, 그래프 겹쳐보기, 표본 로트 수동 대조 등)를 반도체 배경 팀원을 통해 파악·문서화한다.
- **반도체 배경 팀원별로 실제 겪었거나 들어본 단위/시간/조인 실수 사례를 최소 1건씩 수집**한다. 코딩 없이 1주차에 끝낼 수 있으면서, 3.3절의 가설을 약한 실증 수준으로 끌어올리는 가장 효과적인 작업이다.

### 11.2 합성 공정 데이터 + 버그 주입 테스트셋 (Mutation Testing)

실제 fab 데이터에는 접근할 수 없고, 접근하더라도 "일부러 넣은 실수"가 없어 탐지율을 잴 수 없다. 따라서:

1. **공정 데이터 계약에서 합성 데이터를 생성**한다 (로트·웨이퍼 계층, 센서별 다른 샘플링 주기, 표본 측정 계측 포함).
2. 이 데이터를 다루는 **SPC·FDC·수율 분석 스크립트 기본형**을 작성한다.
3. 도메인 팀원이 **"실무자도 바로 알아채기 어려운 수준"의 버그를 주입**한다.
4. **음성 대조군(버그 없는 정상 코드)**을 함께 포함해 오탐률을 측정한다.
5. **블라인드 원칙**: 체커 개발자는 주입된 버그를 미리 보지 않는다. 버그 작성자와 체커 담당자를 분리해 과적합을 막는다.

목표 규모는 유형별 20건 내외 + 음성 대조군이며, 1주차에 팀 합의로 확정한다.

### 11.3 LLM-only Baseline 비교 실험

같은 테스트셋에 대해 세 방식을 나란히 측정한다.

| 비교군 | 설명 |
|---|---|
| (a) 본 시스템 | 공정 데이터 계약 + 정적 규칙 + LLM 하이브리드 |
| (b) LLM-only | "반도체 공정 데이터 관점에서 이 코드를 리뷰해줘" 수준의 도메인 힌트만 준 LLM |
| (c) 범용 도구 | SonarQube, Copilot Code Review 등 |

비교 지표: 탐지율, 오탐률, 동일 입력 반복 시 결과 일관성, 응답 시간, 호출 비용. 설계는 1주차, 실행은 7주차.

### 11.4 리뷰 시간 측정

도메인 팀원을 실무자 대리(proxy) 리뷰어로 삼아, 버그 주입 코드를 **도구 없이 리뷰할 때 vs 도구 리포트와 함께 리뷰할 때**의 소요 시간과 발견율을 비교한다. 실제 fab 엔지니어가 아닌 대리 측정이라는 한계를 결과에 명시한다.

### 11.5 성공 지표

| 지표 | 측정 방법 | 목표 설정 방식 |
|---|---|---|
| 주입 버그 탐지율 | 11.2 테스트셋 | (a)가 (b)·(c)보다 높은지 검증 |
| 오탐률 | 음성 대조군 | (a)의 `error` 등급 오탐률이 12절 Phase 2 진입 기준을 충족하는지 |
| 결과 일관성 | 동일 입력 반복 실행 | (a)의 `error`는 항상 동일해야 함 |
| 비용·지연 | 호출 로그 | (a)가 (b)보다 낮은지 검증 |
| 리뷰 시간 | 11.4 | 도구 사용 시 단축 여부 |

구체적 목표 수치는 현재 근거가 없으므로 미리 단정하지 않고, 1주차 baseline 설계 시 팀이 합의한다.

## 12. CI/CD 적용 로드맵

### 12.1 기본 원칙

> **결정론적인 결과만 파이프라인을 멈출 수 있다. LLM 판단은 언제나 조언으로만 남는다.**

CI 게이트는 같은 코드에 같은 결과를 내야 신뢰를 얻는다. 정적 규칙의 `error`는 이 조건을 만족하지만, LLM의 `warning`은 5.2절에서 스스로 지적했듯 비결정적이다. 공정 데이터 스크립트는 공정 조치로 이어질 수 있는 코드라, 불안정한 게이트는 오히려 도구에 대한 신뢰를 떨어뜨린다.

### 12.2 단계별 로드맵

| 단계 | 시기 | 내용 | 진입 조건 |
|---|---|---|---|
| **Phase 1** | MVP (8주) | PR 코멘트·Slack 알림, 모든 판정은 사람이 확인. **(stretch)** 8주차에 GitHub Actions에서 정적 규칙만 non-blocking으로 실행하는 데모 | — |
| **Phase 2** | MVP 이후 | `error` 등급을 GitHub **required status check**로 승격해 머지 차단. SARIF 출력으로 코드 스캐닝 화면 연동. 계약 기반 **합성 데이터 fixture 테스트** 추가 | 11.2 음성 대조군에서 `error` 오탐률이 팀 합의 기준 이하 |
| **Phase 3** | 확장 | **pre-commit hook**으로 로컬에서 push 전 `error` 사전 확인. Jupyter 노트북 지원(jupytext 등으로 변환 후 분석) | Phase 2 운영 안정화 |

### 12.3 CI/CD 흐름 (Phase 2~3 목표 모습)

```
개발자 commit
    │
    ├─► [pre-commit hook] (Phase 3) 정적 규칙만, 로컬에서 수 초 내 실행
    │
    ▼
PR 생성 ──► GitHub Actions
              ├─ 정적 규칙 엔진 ─────────► error 존재 시 ✗  (required check, 머지 차단)
              ├─ 계약 기반 fixture 테스트 ─► 행 수·키 유일성·커버리지 검사 (required check)
              └─ LLM 판단 (결과 캐시) ────► PR 코멘트 (advisory, 머지 차단 안 함)
    │
    ▼
리뷰어 승인 ──► merge ──► 분석 스크립트·SPC/FDC 룰 운영 환경 반영 (CD)
```

### 12.4 결과 유형별 취급

| 결과 | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| `error` (정적 확정) | PR 코멘트 | **머지 차단** | 로컬 사전 경고 + 머지 차단 |
| `warning` (LLM) | PR 코멘트 | PR 코멘트 | PR 코멘트 |
| `info` (판정 불가) | PR 코멘트 | PR 코멘트 | PR 코멘트 |
| fixture 테스트 실패 | — | **머지 차단** | 머지 차단 |

### 12.5 CI/CD를 위해 필요한 설계 요소

- **억제(suppression) 주석**: 의도된 예외(예: 단위 변환 로직 자체)를 위해 `# fab-review: ignore[FAB-U001] 사유: ...` 형태를 허용하되, **사유 기재를 필수**로 하고 억제 건수를 리포트에 집계한다.
- **LLM 결과 캐싱**: (코드 해시, 계약 버전, 프롬프트 버전)을 키로 캐시해 같은 diff에는 같은 조언이 나오게 하고 비용을 줄인다.
- **diff 기반 분석**: 대형 저장소에서도 CI 시간이 늘지 않도록 변경된 파일·함수만 분석한다.
- **계약의 CI 편입**: 공정 데이터 계약 변경도 PR로 올리고, CI에서 스키마 검증을 통과해야 반영된다. `/rules/propose`는 Phase 2에서 **계약 저장소에 PR을 생성하는 방식**으로 발전시킨다.
- **fixture 테스트**: 계약에서 생성한 합성 공정 데이터로 스크립트의 핵심 병합·집계 로직을 실제 실행해, 정적 분석이 놓친 입도·커버리지 문제를 동적으로 보완한다.
- **LLM 비활성 모드**: 외부 API로 코드를 보낼 수 없는 환경을 위해 정적 규칙만으로 동작하는 모드를 보장한다(15절).
- **SARIF 연동**: GitHub 코드 스캐닝 화면 연동은 저장소 플랜(공개 저장소 또는 GitHub Advanced Security)에 따라 사용 가능 여부가 다르므로, PR 코멘트를 기본 경로로 유지한다.

### 12.6 도구 자체의 CI/CD

11.2절의 버그 주입 테스트셋과 음성 대조군을 **도구 자체의 회귀 테스트**로 재사용한다. 체커나 계약을 수정할 때마다 탐지율이 떨어지거나 오탐이 늘지 않았는지 자동으로 확인하므로, 검증 실험의 산출물이 곧 운영 품질 관리 수단이 된다.
